### 0.4 Orchestration model — who runs in parallel, who runs in sequence

- **Phase 1 (research) is fully parallelizable — it's read-only.** Spawn one subagent per portal (4 total) via Manager View, each working its own page list from Section 1 independently. A 5th subagent starts Section 1.7's ownership-question research and Section 12's per-service backend enumeration simultaneously, since both are also read-only.
- **Phases 2–3 (routes, database) parallelize along the real 15-service boundary in Section 1.1** — one subagent per service. Sequence `analytics-service` **last** in both phases, since its aggregation logic depends on every other service's routes and schema being finalized first (it's the Executive tier — everything else feeds it). Keep frontend route verification as a single subagent's job, since it's one router tree and parallel edits there will conflict.
- **Phase 4 (real-time) is not a per-page parallel task.** Because the real architecture multiplexes all live traffic through exactly `attendance-service` and `notification-service` (1.6), Phase 4 is really two focused subagents — one auditing attendance-service's live QR/OTP session channel, one auditing notification-service's general push channel and every service that should be emitting events into it — rather than N page-by-page subagents inventing N socket rooms.
- **Phase 5 (missing features) parallelizes along the backlog table's "Primary service(s)" column** (Section 6) — disjoint services run concurrently; anything touching a shared service gets sequenced. The AI-feature cluster (1.7) is a single dedicated track, gated on the STOP condition being resolved first.
- **Phase 6 (bug sweep) parallelizes by bug pattern (6 subagents), not by page**, run after Phases 1–5 close.
- **Shared/common code is the one place per-service parallelism breaks down.** If multiple services import a shared middleware, a shared types package, or a shared utils module (common in a `packages/shared`-style folder), assign that folder to whichever service's subagent needs it first, and have every other subagent treat it as read-only until that change merges to the integration branch. Two parallel subagents editing the same shared file on two different branches is exactly the class of conflict per-service branching is meant to avoid — don't let it happen silently.
- Give each parallel track its own branch or Antigravity workspace; merge into an integration branch at each phase gate. See 15.3 for the concrete branch list, now using real service names.

## 1.6 Cross-cutting architectural features (confirmed from the source doc — treat as ground truth, not convention-to-invent)

### Command Palette (cmd+k)

Available in all portals. Indexes courses, pages, and discussions, routing to the correct React route instantly. No single owning service is named for the search index itself — see 1.7.

### Real-time Socket.IO — centralized, not per-page

> Architecture note (from the real spec)
>
> All portals maintain active socket connections multiplexed to exactly TWO services: attendance-service and notification-service. This is a materially different model from a generic 'every page can have its own room' convention — no other service is described as running a socket layer.
> Practical implication for Phase 4/5: a feature that wants a live update (discussion upvotes, placement status changes, library due-soon alerts) should get there by having its owning service emit an event that notification-service relays over the existing multiplexed connection — not by that service opening a second, competing socket server. Attendance-service's channel is specific to its own live QR/OTP check-in session flow.

### Idempotency via compound unique indices

> Architecture note (from the real spec)
>
> All critical writes — attendance, leave, payments, placement — use compound unique indices in MongoDB to prevent race conditions natively. This is the confirmed established pattern for 'exactly-once' style records in this codebase, and it's a stronger, more specific guarantee than a generic application-level 'check then write' guard. Section 4 and Section 7 build directly on this.

Pattern 2 below is now shown using the confirmed EduSphere convention (compound unique index) rather than a generic atomic-counter fix, since 1.6 confirms which pattern this codebase actually uses for exactly-once writes. ### Client-trusted values for approval/scoring/eligibility/authorization

```javascript
// BAD
app.post('/grades', (req, res) => {
  const { studentId, score, approvedBy } = req.body;
  Grade.create({ studentId, score, approvedBy }); // approvedBy from client!
});

// GOOD
app.post('/grades', requireRole('faculty'), (req, res) => {
  const { studentId, score } = req.body;
  Grade.create({ studentId, score, approvedBy: req.user.id }); // from verified JWT
});
```

### Race conditions on exactly-once writes — the confirmed EduSphere pattern

```javascript
// BAD (attendance check-in, application-level check only)
const existing = await Attendance.findOne({ studentId, sessionId });
if (!existing) {
  await Attendance.create({ studentId, sessionId, status: 'present' }); // two concurrent requests can both pass the check
}

// GOOD — compound unique index does the enforcement, not application logic
// schema: attendanceSchema.index({ studentId: 1, sessionId: 1 }, { unique: true })
try {
  await Attendance.create({ studentId, sessionId, status: 'present' });
} catch (err) {
  if (err.code === 11000) return res.status(409).json({ error: { code: 'ALREADY_CHECKED_IN' } });
  throw err;
}
// Same pattern applies to leave requests, payment records, and placement applications (1.6).
// For pure capacity counters (course seats, library copies) where no compound-unique-index
// applies, use an atomic conditional update instead:
await Course.updateOne(
  { _id: id, $expr: { $lt: ['$enrolled', '$capacity'] } },
  { $inc: { enrolled: 1 } }
);
```

### Paginated-subset math presented as a full aggregate

```javascript
// BAD (analytics-service)
const page = await Grade.find().limit(20);
const avg = page.reduce((a,g)=>a+g.score,0)/page.length; // only first 20 — this is exactly the 'fake math'
// the source spec explicitly warns against for Analytics & Reports


// GOOD
const [{ avg }] = await Grade.aggregate([
  { $group: { _id: null, avg: { $avg: '$score' } } }
]); // computed over the full collection — matches the spec's own 'live dynamic Mongo
// aggregations (no fake math)' requirement for Management's Analytics & Reports page
```

### Authorization scoping trusted from client parameters instead of authenticated identity

```javascript
// BAD
app.get('/leaves', (req, res) => {
  const { studentId } = req.query; // client can pass anyone's id
  Leave.find({ studentId });
});

// GOOD
app.get('/leaves', requireRole('student'), (req, res) => {
  Leave.find({ studentId: req.user.id }); // scoped to the authenticated user
});
```

### String-based date comparisons instead of proper Date types

```javascript

// GOOD
if (new Date(req.body.dueDate) > new Date('2026-08-18')) { ... }
```

### 13.3 Role model quick reference — 5 roles, CONFIRMED by the architecture doc

| Role | Portal | Can generally... | Cannot... |
|---|---|---|---|
| `student` | Student | view/submit own data, enroll, request leave, apply to placements | see other students' records, approve anything, modify grades |

| `management` | Management | view aggregated analytics **and** write for governance approvals (Approval Center, Course Approvals, Budget Overview) | modify operational records outside the approval workflows — this role is not purely read-only, correct that assumption if it appears elsewhere |

# 14. SUPPLEMENTARY CHECKLISTS

### 14.1 Security checklist

- No secrets committed to the repo or exposed via any API response.
- Password hashing uses bcrypt/argon2 with an appropriate cost factor.
- Rate limiting on auth-service's login/reset/registration endpoints — explicitly named in its own spec description, so its absence is a direct spec violation, not just a best practice gap.
- File upload endpoints (assignment-service submissions, course-service materials, certificate-service outputs) validate MIME type and size server-side.
- CORS configured to real known origins.
- All Mongoose queries use parameterized filters.
- Every privileged action is captured in Admin's Audit & Logs page with actor, target, timestamp — and specifically test that `super_admin`-only actions (Backup & Restore, Configuration) are logged with that distinction visible, not merged into a generic 'admin action' entry.

### 14.2 Performance checklist

- Every list endpoint supports pagination.
- Every N+1 finding has a corresponding fix with a verified reduced query count.
- analytics-service's dashboards use cached/TTL'd aggregation, not live per-request recomputation of expensive queries — while still honoring 'no fake math' (the cache must hold a real computed value, not a placeholder).
- Large exports (Certificates, Reports Center, Executive Reports) run as background jobs if they risk request timeout.
- If the Command Palette (1.7) ends up fanning out across services per keystroke, confirm it's debounced and parallelized, not sequential.

### 14.3 Accessibility & UX checklist

- Every form has associated labels.
- Every async action shows loading and distinct success/error states.
- Empty states are explicit and honest — 'No grades posted yet' rather than a zeroed chart.
- Color is never the sole indicator of status.

### 14.4 Final live walkthrough script

Execute as the literal last step before signing off Deliverable 8:

- Log in as `student` → visit every page in Section 1.2 in module order → perform at least one meaningful action per page → log out.
- Log in as `faculty` → visit every page in Section 1.3 → perform at least one meaningful action per page, including approving the leave request submitted above (once 1.7 confirms who owns approval) → log out.
- Log in as `admin` → visit every page in Section 1.4 that doesn't require `super_admin` → confirm the super_admin-only pages correctly reject this account → log out.
- Log in as `super_admin` → visit the remaining Section 1.4 pages, including Configuration and Backup & Restore (view only — do not actually execute a restore) → log out.
- Log in as `management` → visit every page in Section 1.5, confirming the faculty grade submitted above surfaces correctly in Student Performance and the leave request surfaces nowhere it shouldn't → test at least one write path (e.g. Approval Center) to confirm Management's write access for approvals actually works, not just its read views → log out.
- Record every step's outcome in Deliverable 8 using the 3.6 PASS/FAIL format.
