PART 18 — MICROSERVICES ARCHITECTURE (NEW)
====================================================================

Redesign backend as a service-oriented architecture.

Each microservice owns:
  - Its own database collections (or subset)
  - Its own REST API endpoints
  - Its own business logic
  - Event producers/consumers
  - Independent deployment
  - Separate scaling strategy

SERVICES DEFINED

1. API GATEWAY SERVICE (new entry point, Part 19)
   - Reverse proxy for all requests
   - Authentication forwarding
   - Rate limiting
   - Load balancing
   - Request logging
   - Response compression
   - Versioning orchestration
   Owns: nginx.conf, gateway middleware

2. AUTHENTICATION SERVICE (extracted from monolith)
   Responsibilities:
     - User registration (student only)
     - Login / logout
     - JWT token generation / refresh
     - Email verification
     - Password reset
     - OAuth integration (future)
     - 2FA (future)

     POST   /auth/register
     POST   /auth/login
     POST   /auth/refresh
     POST   /auth/logout
     POST   /auth/forgot-password

     GET    /auth/verify-email/:token
     GET    /auth/me

SERVICE COMMUNICATION PATTERNS

Synchronous (REST):
  - API Gateway calls services directly for immediate responses
  - Service-to-service REST calls for queries (course service asks
    enrollment service for course enrollment count)

Asynchronous (Events):
  - All state changes are published as domain events
  - Other services subscribe and react asynchronously
  - RabbitMQ or Apache Kafka for event broker
  - Dead-letter queues for failed events

Example event flow:
  1. Student submits assignment
  2. Assignment Service publishes: assignment.submitted event
  3. Notification Service consumes event -> creates notification
  4. Analytics Service consumes event -> updates student metrics
  5. Audit Service consumes event -> logs the action
  6. (All happen asynchronously, no blocking)

PART 19 — API GATEWAY & REDIS ARCHITECTURE (NEW)
====================================================================

API GATEWAY (Kong, Traefik, or custom nginx)

Responsibilities:
  - Single entry point: gateway.edusphere.com
  - Route requests to appropriate microservice
  - Enforce authentication (forward JWT from client)
  - Rate limiting (100 req/min per user, 1000 req/min per IP)
  - Request logging (Loki integration, Part 26)
  - Response compression (gzip)
  - Load balancing across service replicas
  - Circuit breaker (if a service is down, fail gracefully)
  - Request timeout (30s global)
  - Header validation (cors, content-type, etc)

Config example:
  /api/v1/auth/*        -> Auth Service (port 3001)
  /api/v1/users/*       -> User Service (port 3002)
  /api/v1/courses/*     -> Course Service (port 3003)
  /api/v1/enrollments/* -> Enrollment Service (port 3004)
  /api/v1/attendance/*  -> Attendance Service (port 3005)
  /api/v1/assessments/* -> Assessment Service (port 3006)
  /api/v1/assignments/* -> Assignment Service (port 3007)
  /api/v1/certificates/*-> Certificate Service (port 3008)
  /api/v1/notifications/* -> Notification Service (port 3009)
  /api/v1/reports/*     -> Analytics Service (port 3010)
  /api/v1/search/*      -> Search Service (port 3011)
  /api/v1/audit-logs/*  -> Audit Service (port 3012)
  /api/v1/admin/*       -> Multiple services (admin endpoints)

REDIS CACHE LAYER

Integrate Redis 7.0+ for distributed caching.

Cache keys (with TTL):

  Courses:
    courses:published          (1 hour) — list of all published courses
    courses:search:term        (30 min) — search results
    courses:{courseId}         (1 hour) — course details
    courses:{courseId}:content (1 hour) — course materials

  Enrollments:
    enrollments:user:{userId}  (30 min) — student's enrolled courses
    enrollments:course:{courseId} (1 hour) — enrolled students in course

  Attendance:
    attendance:course:{courseId}:{date} (1 day) — daily attendance
    attendance:student:{studentId}:{semester} (7 days) — student attendance %
    attendance:leaderboard:{courseId} (1 day) — highest attendance students

  Dashboard Data:
    dashboard:student:{userId} (15 min) — cached stat cards
    dashboard:faculty:{userId} (15 min) — cached teaching overview
    dashboard:admin          (30 min) — cached admin stats
    dashboard:management     (1 hour) — cached executive KPIs

  Notifications:
    notifications:unread:{userId} (5 min) — unread count
    notifications:{userId}     (10 min) — recent notifications

  Quiz Leaderboards:
    leaderboard:quiz:{assessmentId} (1 day) — top scorers

  Session Cache:
    sessions:{sessionId}       (7 days) — refresh token metadata
    active_users:online        (realtime) — connected users (Socket.IO)

Cache Invalidation Strategy:
  - Automatic on TTL expiry
  - Manual invalidation on state change (event-driven)
    Example: when attendance is marked, invalidate
    attendance:student:*, attendance:leaderboard:*
  - Namespace-based invalidation for bulk clears

Performance Benefits:
  - Dashboard load time: 200ms (with cache) vs 2000ms (without)
  - Course search: 50ms (with cache) vs 500ms (without)
  - Attendance page: 100ms (with cache) vs 1000ms (without)

PART 20 — REAL-TIME COMMUNICATION WITH SOCKET.IO (NEW)
====================================================================

Integrate Socket.IO for real-time, bidirectional events.

Real-Time Events (server → client push)

  Notifications:
    notification:new          — new in-app notification
    notification:read         — someone read your message
    announcement:new          — new announcement posted

  Live Class:
    class:started             — faculty started a class
    class:ended               — class ended
    attendance:marked         — your attendance was marked
    attendance:alert          — low attendance warning

  Assignments & Assessments:
    assignment:posted         — new assignment in your course
    assignment:submitted      — your assignment received
    assessment:published      — new quiz available
    quiz:result_ready         — your quiz is graded

  Certificates:
    certificate:generated     — your certificate is ready
    certificate:revoked       — a certificate was revoked

  Chat (future):
    message:new               — new message in course chat
    typing:indicator          — someone is typing
    user:online               — user came online
    user:offline              — user went offline

  Admin/Management:
    course:approved           — course was approved
    course:rejected           — course was rejected
    system:alert              — system health warning
    audit:suspicious          — suspicious activity detected

Socket Connections

  Client connects on login:
    io.connect('https://edusphere.com/socket', {
      auth: { token: jwtAccessToken }
    })

  Server authenticates token in socket middleware.

  Join specific rooms based on role:
    student:1234              — for student ID 1234
    faculty:5678              — for faculty ID 5678
    course:CS101              — for all students/faculty in CS101
    admin                     — for all admins
    management                — for all management
    notifications:{userId}    — for user-specific notifications

Real-Time Interactions

  Student scanning QR for attendance:
    1. Frontend emits: attendance:qr_scan { token, courseId }
    2. Backend validates token
    3. Backend broadcasts to course:CS101 room:
       attendance:marked { studentId, status: present }
    4. Faculty sees it in real-time on attendance page

  Faculty publishing a quiz:
    1. Frontend emits: quiz:publish { assessmentId }
    2. Backend publishes event
    3. All subscribed students see in notification bell
    4. Dashboard updates in real-time

  Live leaderboard during quiz:
    1. As students submit, backend updates assessment results
    2. Emits: leaderboard:updated { topScores }
    3. Viewing students see live rank updates

Socket.IO Adapter for Horizontal Scaling

  Use Socket.IO Redis adapter (socket.io-redis) so that
  even if a student connects to server A and another to server B,
  they can still communicate via shared Redis pub/sub.

PART 21 — ENTERPRISE SEARCH (NEW)
====================================================================

Create Global Search Service with Elasticsearch or Meilisearch.

SEARCHABLE ENTITIES
  - Students (name, ID, email, department)
  - Faculty (name, ID, email, department, courses)
  - Courses (title, code, description, faculty, department)
  - Departments (name, code, courses, faculty)
  - Certificates (certificate ID, student name, course, date)
  - Announcements (title, body, posted date, author)
  - Assignments (title, course, due date)
  - Assessments (title, course, date)
  - Support Tickets (subject, description, status)
  - Library Books (future — title, ISBN, author, category)
  - News (title, body, date)

SEARCH FEATURES
  - Global search with single query box
  - Type-aware search (search in "Courses only" or "All")
  - Autocomplete suggestions as user types
  - Recent searches (per user, last 10)
  - Filters/facets:
    * By type (Course, Student, Faculty, etc)
    * By department
    * By status
    * By date range
  - Full-text search (partial word matching, typo tolerance)
  - Ranked results (relevance, date, popularity)
  - Search analytics (what are users searching for?)

EXAMPLE QUERIES
  - "Database"
    Results: Database Systems (course), John Database (student),
             Prof. Data (faculty), Database Admin (course), etc
             Sorted by relevance

  - "CS 101"
    Results: CS101 (course), CS101A (section), CS101 Quiz, etc

  - "machine"
    Results: Machine Learning (course), Machine Learning PDF (material),
             related assignments, etc

  - "john"
    Results: John Smith (student), John Doe (faculty), John's Certificate, etc

BACKEND ARCHITECTURE
  1. Elasticsearch/Meilisearch runs in Kubernetes (Part 25)
  2. Search Service indexes documents
  3. On entity creation/update, publish event
  4. Event triggers index update in Elasticsearch
  5. Search queries hit Elasticsearch directly (fast)
  6. Results transformed and returned to client

API Endpoints:
  GET /search?q=query&type=all|courses|students|faculty&limit=20
  GET /search/autocomplete?q=term
  GET /search/recent
  DELETE /search/recent/:id (clear specific search)

PERFORMANCE
  - Search results returned in <100ms
  - Typo tolerance for better UX
  - Facet counts updated in real-time

Secrets:
  - db-credentials (MongoDB user/pass)

  - mail-credentials (SMTP user/pass for nodemailer)

  - redis-password (Redis auth)
  - service-api-keys (inter-service communication keys)

PersistentVolumes & PersistentVolumeClaims:
  - MongoDB data: 500GB volume
  - Redis data: 50GB volume
  - Elasticsearch data: 200GB volume
  - File uploads: 1TB volume (for dev/demo; prod uses S3)

Service Accounts & RBAC:
  - api-gateway-sa (can read ConfigMaps, manage services)
  - services-sa (can write logs, read secrets)
  - admin-sa (elevated permissions for admin tasks)

Readiness & Liveness Probes:
  - Readiness: /health endpoint (checks if service is ready)
  - Liveness: /live endpoint (checks if service is alive, restarts if not)
  - InitialDelaySeconds: 30s
  - PeriodSeconds: 10s
  - TimeoutSeconds: 5s

Resource Requests & Limits:
  - Small services (auth, user): 256Mi RAM / 100m CPU (request) - 512Mi / 500m (limit)
  - Medium services (course, enrollment): 512Mi RAM / 200m CPU - 1Gi / 1000m

Network Policies:

  - Allow monitoring stack to scrape metrics

Rolling Updates:

Pod Disruption Budgets:
  - Min 1 pod available during cluster maintenance
